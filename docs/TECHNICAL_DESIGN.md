# Technical Design: Goodnumbers Weekly Health Journal

**Version:** 0.3
**Author:** AI Assistant & User
**Status:** In Progress

## 1. Overview

This document outlines the technical architecture and key design decisions for the Goodnumbers application, an experimental weekly health journal for Type 1 Diabetics. The goal is to build a Minimum Viable Product (MVP) that is secure, robust, and can be self-hosted on a single machine using open-source technologies.

## 2. Core Technology Stack

The application will be built using the following primary technologies:

- **Backend Framework:** Express.js
- **Frontend Framework:** React
- **Database:** SQLite
- **ORM:** Prisma
- **Authentication:** Auth.js (formerly NextAuth.js)
- **Deployment:** Docker container on a single Google Compute Engine (GCE) instance.

## 3. System Architecture

The system is designed as a monolithic application running within a single Docker container. It comprises two main, concurrently running processes managed by `pm2`.

### 3.1. Web Server Process

- **Responsibility:** Handles all incoming HTTP requests from users. This includes serving the React frontend, handling API calls, and managing user authentication.
- **Implementation:** An Express.js application.

### 3.2. Background Worker Process

- **Responsibility:** Executes long-running, resource-intensive tasks, specifically the "Journal Generation Process". This decouples heavy processing from the user-facing web server, preventing request timeouts and improving reliability.
- **Implementation:** A Node.js script utilizing the **BullMQ** library to process jobs from a queue.

### 3.3. Job Queue

- **Responsibility:** Mediates between the Web Server and the Background Worker. When a user requests a new journal, the web server places a "job" onto the queue. The worker picks up this job and executes it.
- **Implementation:** **BullMQ** with a **Redis** instance serving as the queue's backend. Both Redis and the BullMQ worker will run on the same GCE instance.

### 3.4. Database

- **Responsibility:** Provides persistent storage for all application data, including user accounts, journal entries, and application settings.
- **Implementation:** A **SQLite** database file stored on the GCE instance's local filesystem.
- **Concurrency Tuning:** To mitigate file locking issues between the web server and the worker, the Prisma client will be configured to enable **Write-Ahead Logging (WAL)** mode upon connection. The following PRAGMA directives will be executed:
  ```sql
  pragma journal_mode = WAL;
  pragma synchronous = normal;
  pragma temp_store = memory;
  pragma mmap_size = 30000000000;
  ```

## 4. Data Models (Schema)

This section outlines the core data structures for the application using Prisma schema syntax.

### 4.1. Journal Model

The `Journal` model stores user inputs, generated content, and progress for a single weekly entry.

```prisma
model Journal {
  id        String   @id @default(cuid())
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  // Ownership
  user   User   @relation(fields: [userId], references: [id])
  userId String

  // Job Progress
  status    String @default("PENDING") // PENDING, PROCESSING, COMPLETE, FAILED
  progress  Int    @default(0)
  statusMessage String? // "Fetching data...", "Running analysis..."

  // User Inputs
  weeklyVibe          String?   // "Wilted", "Sprouting", "Thriving", "Blooming"
  influencingFactors  Json?     // ["Busy", "Poor Sleep", "Travel"]
  goalsForNextWeek    String?

  // Generated Content
  podcastTitle        String?
  podcastDescription  String?
  podcastAudioUrl     String?
  agpChartData        Json?
  analysisInsights    Json? // For structured text analysis and insights
}
```

### 4.2. GlycemicEventCluster Model

The `GlycemicEventCluster` model stores a detected pattern of recurring glycemic events. Each record corresponds to a `TimeCluster` object generated by the analysis pipeline.

```prisma
model GlycemicEventCluster {
  id        String   @id @default(cuid())
  journal   Journal  @relation(fields: [journalId], references: [id])
  journalId String

  // For querying, sorting, and summary display
  eventType       GlycemicEventType // From the TimeCluster
  eventCount      Int               // From the TimeCluster
  meanTimeMinutes Int               // Average time of day (0-1439)

  // The full TimeCluster object, including all classified events within it
  clusterDataJson Json
}
```

## 5. Analysis Pipeline Summary

The backend analysis pipeline is responsible for processing raw Nightscout data into actionable insights and clustered patterns. The process, as derived from the existing prototype code, follows these steps:

1.  **Data Preparation (`gn-autotune-prep.ts`):** Raw Nightscout entries and treatments are processed into categorized glucose data streams (`AutotunePreppedData`).
2.  **Event Detection (`detect_events.ts`):** The prepared glucose data is analyzed against dynamic, patient-specific ranges to identify a flat list of individual `GlycemicEvent` objects (e.g., a single instance of HYPOGLYCEMIA).
3.  **Event Classification (`event_classifier.ts`):** Each `GlycemicEvent` is further analyzed to add contextual classifications. For example, a `HIGH` event is classified based on its proximity to meals and boluses, resulting in types like `HIGH_AFTER_UNCOVERED_MEAL`.
4.  **Time-Based Clustering (`time_clustering.ts`):** The classified events are then grouped by time of day into `TimeCluster` objects. A cluster represents a recurring pattern of a specific event type (e.g., "Highs that happen frequently around 8:30 PM"). These `TimeCluster` objects are the final data structures persisted in the `GlycemicEventCluster` table.

## 6. API Endpoints

The backend will expose a RESTful API for the frontend. All endpoints will be protected by authentication middleware to ensure a valid user session exists.

### 6.1. `POST /api/journals`

- **Purpose:** Initiates the generation of a new weekly journal.
- **Logic:**
    1.  Verifies the user is authenticated.
    2.  Performs rate-limiting and concurrency checks (e.g., user can only create one journal every 3 days and cannot have one already processing).
    3.  Creates a new `Journal` record in the database linked to the session `userId`.
    4.  Enqueues a job in BullMQ for the background worker, passing the new `journalId`.
- **Security:** Uses anti-CSRF token protection. Authorization is handled by using the `userId` from the server session.

### 6.2. `GET /api/journal-status/:id`

- **Purpose:** Allows the client to poll for the progress of a journal being generated.
- **Logic:**
    1.  Verifies the user is authenticated.
    2.  Finds the `Journal` by its `id`.
    3.  Performs an ownership check to ensure the journal's `userId` matches the session `userId`.
- **Security:** The ownership check prevents users from probing the status of other users' jobs. Returns a `404 Not Found` if the journal doesn't exist or is not owned by the user.

### 6.3. `GET /api/journals`

- **Purpose:** Fetches a summarized list of all completed journals for the user's dashboard.
- **Logic:**
    1.  Verifies the user is authenticated.
    2.  Queries for all journals where the `userId` matches the session `userId`.
    3.  Orders the results by creation date, newest first.
- **Response:** Returns an array of `Journal` objects with a subset of fields suitable for a list view (e.g., `id`, `createdAt`, `podcastTitle`, `podcastDescription`).

### 6.4. `GET /api/journals/:id`

- **Purpose:** Fetches the complete data for a single journal report.
- **Logic:**
    1.  Verifies the user is authenticated.
    2.  Finds the `Journal` by its `id` and performs an ownership check.
    3.  The database query will include the related `GlycemicEventCluster` records.
- **Response:** Returns the full `Journal` object along with all its associated `GlycemicEventCluster` data.

## 7. Security Considerations

### 7.1. Credential Encryption

To ensure the security of sensitive user data, the `nightscoutToken` will be encrypted at rest in the database.

- **Method:** Symmetric encryption will be used via Node.js's built-in `crypto` module (e.g., AES-256-GCM).
- **Key Management:** A single, strong, 256-bit secret encryption key will be generated and stored exclusively as an environment variable (`ENCRYPTION_KEY`) on the production server. This key will not be checked into source control.
- **Process:**
    1.  When a user submits their Nightscout token, the API backend will encrypt it using the `ENCRYPTION_KEY`. An initialization vector (IV) will be generated for each encryption and stored alongside the encrypted token to ensure strong security.
    2.  When the background worker needs the token to fetch data from a user's Nightscout instance, it will retrieve the encrypted token and the IV from the database and decrypt it in memory immediately before use. The plaintext token will not be logged or stored elsewhere.
